## 1. 功能概览

管理后台是一个自包含的单页 HTML 应用，运行在 `wecom-archive-api` Docker 容器内（端口 `18190`）。提供以下功能：

- **群聊列表**: 左侧栏列出全部已归档群聊，含消息数、参与人数和最后活跃时间
- **对话还原**: 选中群聊后以聊天气泡形式按时间升序展示消息，含文字、图片、视频、语音、文件等类型
- **自动刷新**: 每 30 秒自动拉取最新消息，可手动开关
- **群名称编辑**: 双击群名称可自定义命名，持久化到数据库
- **消息搜索**: 输入关键词过滤群聊列表
- **消息导出**: 支持单个群聊和全部群聊的 Markdown + 源文件 + 媒体附件打包下载

- **请用域名访问**（证书是 `admin.jsyzz.com` 的）；用 IP 会报证书不匹配

**链路**：
```
公网 → 阿里云安全组 TCP 18192 → NPM 容器 0.0.0.0:18192
   → [HTTPS 解密 + auth_basic 密码校验] → wecom-archive-api:18190 (docker 内网)
```

三层防护：独立端口 18192（非常规）+ Basic 密码 + HTTPS 加密。后端 `wecom-archive-api` 仍只绑 `127.0.0.1:18190`，不直接暴露。

**前置条件**：阿里云安全组须放行 **TCP 18192**（云端防火墙，SSH 改不了，需在 ECS 控制台配置）。宿主 iptables 已全开放。

## 4. 消息导出

### 4.1 单个群聊导出

1. 点击左侧栏选中目标群聊
2. 在右侧工具栏点击「⬇ 下载本群全部」
3. 浏览器下载 ZIP 压缩包

**ZIP 包结构**:

```
wecom-{roomid}.zip
└── {roomid}/
    ├── README.md              # Markdown 格式群聊记录
    ├── messages/              # 每条消息的 JSON 源文件
    │   ├── seq_1/
    │   │   └── message.json   # 企业微信 SDK 原始消息数据
    │   ├── seq_2/
    │   │   └── message.json
    │   └── ...
    └── media/                 # 媒体附件（按类型分目录）
        ├── image/             # 图片（.jpg, .png 等）
        ├── video/             # 视频（.mp4 等）
        ├── voice/             # 语音（.amr 等）
        ├── file/              # 文档（.docx, .pdf, .xlsx 等）
        └── emotion/           # 表情
```

### 4.2 全部群聊导出

1. 点击左侧栏「⬇ 导出全部群聊」按钮
2. 等待生成（数据量大可能耗时较长）
3. 浏览器下载 ZIP 压缩包

**ZIP 包结构**:

```
wecom-all-rooms-YYYYMMDD.zip
├── INDEX.md                  # 总索引：群聊列表 + 消息数统计
└── rooms/
    ├── {roomid_1}/
    │   ├── README.md
    │   ├── messages/...
    │   └── media/...
    ├── {roomid_2}/
    │   └── ...
    └── ...
```

### 8.6 媒体下载卡死根治（2026-07-30，重要）

**这是导致归档"页面停留旧日期、不再更新"的根因及修复。**

#### 症状
- 页面停留在某个旧日期，`fetched_seq` 在涨但 `committed_seq` 不动
- `journalctl -u wecom-archive.service` 反复出现 `ARCHIVE_SKIP reason=lock_held_by_other`
- 有 `wecom-archive-once-*` 容器 `Up` 数小时/数天不退出

#### 根因
`stage_upload_media` 的 `load_targets` 会捞起**所有** `PENDING`/`RETRY_WAIT` 状态的媒体。只要队列里有一个"毒文件"（超大安装包如 `.zip`、长录音如 `.m4a`），企业微信 SDK 的 `GetMediaData` 就会**永久挂起**：进程占着 advisory lock 不放 → 后续每分钟轮次全部 SKIP → 归档停摆。**即使本轮新消息 `media_refs=0`，每轮仍会拉起毒文件重试挂起。** API 只显示 `processing_status='READY'` 的消息，所以页面停在最后 READY 的日期。

挂起点在 `STAGE_JSON` 之后、`STAGE_MEDIA` 打印之前（`load_targets` / `process_one` → `GetMediaData` 内）。

#### 根治（两层，缺一不可）
1. **墙钟超时**：`scripts/upload_media_once.py` 的 `download_media` 加了墙钟上限 `MEDIA_WALL_TIMEOUT`（默认 180s，`time.monotonic()` 检查），超时抛 `RuntimeError` → `_mark_retry` → 继续下一个，不再永久挂起。
2. **毒文件豁免**：把下载不了的毒文件移出下载队列——标 `processing_status='WAIVED'`（媒体状态枚举之一）。

#### 媒体 `processing_status` 枚举（CHECK 约束 `ck_wecom_archive_media_status`）
`PENDING` / `DOWNLOADING` / `DOWNLOADED` / `UPLOADING` / `UPLOADED` / `VERIFIED` / `RETRY_WAIT` / `FAILED_BLOCKING` / `WAIVED`
> ⚠️ **没有 `FAILED`**，写 `FAILED` 会违反 CHECK 约束报错。要跳过毒文件用 **`WAIVED`**。

#### 应急恢复步骤（若再次卡死）
```bash
# 1. 杀掉卡死的归档轮容器
docker ps -q --filter "name=wecom-archive-once" | xargs -r docker rm -f

# 2. 清掉残留的 advisory lock 会话
export PGPASSWORD="$(cat /opt/wecom-msgaudit-archive/secrets/db_password)"
docker exec -e PGPASSWORD="$PGPASSWORD" lawfirm-trial-server-postgres-1 \
  psql -U lawfirm_trial -d lawfirm_system_trial -c \
  "SELECT pg_terminate_backend(pid) FROM pg_stat_activity
    WHERE pid IN (SELECT pid FROM pg_locks WHERE locktype='advisory') AND pid<>pg_backend_pid();"

# 3. 找出卡死的毒媒体（长时间 RETRY_WAIT 的大文件），标 WAIVED 移出队列
docker exec -e PGPASSWORD="$PGPASSWORD" lawfirm-trial-server-postgres-1 \
  psql -U lawfirm_trial -d lawfirm_system_trial -c \
  "UPDATE wecom_archive.media SET processing_status='WAIVED',
     last_error_code='getmediadata_hang_waived', updated_at=CURRENT_TIMESTAMP
    WHERE id IN (<毒媒体id>) AND processing_status IN ('PENDING','RETRY_WAIT');"

# 4. 触发一轮，应完整走完 STAGE_FETCH→MEDIA→FINALIZE→END 且 committed 追平
systemctl start wecom-archive.service
```

#### 单独补某个豁免的媒体（之后想重新下载时）
```bash
# 先改回 RETRY_WAIT，再定点处理（墙钟超时生效，下不动会安全放弃）
docker exec -e PGPASSWORD="$PGPASSWORD" lawfirm-trial-server-postgres-1 \
  psql -U lawfirm_trial -d lawfirm_system_trial -c \
  "UPDATE wecom_archive.media SET processing_status='RETRY_WAIT' WHERE id=<media_id>;"
# 然后跑 upload_media_once.py --media-id <media_id>
```

### 9.3 前端 API base 修复（2026-07-30）

**症状**：公网访问 `https://admin.jsyzz.com:18192/admin` 时页面框架能开，但群聊列表"加载中…"后提示"加载失败"。

**根因**：前端 JS 里 API 地址被硬编码成 `:18190`——
```js
// 修复前（错误）：非 /wecom-admin 路径时跳到 18190（公网未开）
var API = isProxy ? (origin + '/wecom-admin-internal') : (origin.replace(/:\d+$/, '') + ':18190');
```
页面经 18192 加载，但 JS 却去请求 `admin.jsyzz.com:18190/...`（公网没开）→ 失败。

```js
var API = isProxy ? (window.location.origin + '/wecom-admin-internal') : window.location.origin;
```
改后须 `docker restart wecom-archive-api`；浏览器需强制刷新（`Ctrl+Shift+R`）清掉旧 JS 缓存。

## 10. 数据流与安全

### 10.1 每轮归档流程（A→K）

```
timer 每分钟整点触发
    │
    ▼
A. advisory lock 互斥（pg_try_advisory_lock，防并发）
B. GetChatData(fetched_seq) — 从 SDK 增量拉加密消息
C. 幂等落库（message + message_payload），已存在则跳过
D. DecryptData 解密 → normalize → 登记 media 任务
E. 上传 message.json → OSS（HEAD 预检 + SHA-256 比对）
F. GetMediaData 下载原件 → 上传 OSS
G. 回填 verified_media_count → 状态置 READY
H. 推进 committed_seq（连续区间，遇 gap 止于缺口前）
I. 错误汇总（processing_error 未解决项）
J. 输出 SUMMARY 日志
K. 释放 advisory lock
```

### 10.2 安全设计

| 层面 | 措施 |
|---|---|
| **密钥** | 仅通过 `0400` 权限文件挂载，绝不写入代码/镜像/日志/环境变量 |
| **日志** | 仅输出 seq/计数/object_key/sha16，不输出聊天正文、SDK fileid、CorpID、Secret、私钥 |
| **OSS** | Bucket 私有，访问仅通过临时签名 URL（60-3600s） |
| **后端端口** | `18190` 仅绑定 `127.0.0.1`，不直接对外暴露 |
| **公网访问** | NPM 反代 `0.0.0.0:18192`，HTTPS 加密 + HTTP Basic 密码 + 非常规端口，三层防护（2026-07-30 起） |
| **密码存储** | Basic Auth 凭据以 apr1-MD5 哈希存于 `wecom_18192.htpasswd`，非明文 |
| **路径脱敏** | roomid / conversation_key 以 SHA-256 前 16 位入路径 |
| **并发** | `pg_try_advisory_lock` 防多实例，重叠触发自动 SKIP |
| **数据不变** | 首次写入后绝不覆盖，后续重入仅校验一致性（幂等） |
| **游标保护** | `FOR UPDATE` 行锁，绝不回 seq=0 |
| **媒体下载** | `MEDIA_WALL_TIMEOUT` 墙钟超时防大文件挂起卡死整轮（见 §8.6） |

### 10.3 关键不变量

- 每轮从 `archive_cursor.fetched_seq` 续拉，绝不重置
- `fetched_seq = committed_seq` 表示零积压
- `pg_try_advisory_lock` 保证单轮唯一
- 同内容 → `ALREADY_VERIFIED`，异内容 → `OssContentConflict`（禁止覆盖）
