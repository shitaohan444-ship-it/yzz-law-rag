## 5. 测试期间发现的问题

### 5.1 VL 响应 JSON 解析失败

**现象**

```text
VL returned invalid JSON (JSONDecodeError)
```

**范围判断**

- MinIO 派生图已生成。
- PostgreSQL 图片记录已创建。
- Logo 调用同一模型成功。
- 失败点位于 VL 响应内容解析。

**处理结果**

修改代码后重启 API，文档 20 与正确中文文档 21 均成功入库，流程图分类、描述、向量和检索通过。

### 5.2 PowerShell 生成测试图时中文变成问号

**原因**

Windows PowerShell 5.1 将含中文的 here-string 通过管道传给 Python 时发生字符编码丢失。

**处理结果**

Python 源码改为 ASCII + Unicode 转义，重新生成文档 21。目视检查与 VL OCR 均确认中文正确。

### 5.3 PowerShell HTTP 响应显示乱码

**原因**

Windows PowerShell 5.1 对 UTF-8 JSON 响应采用了错误解码方式。

**处理结果**

改用 `.NET HttpClient`，请求使用 UTF-8，响应字节显式按 UTF-8 解码。API、数据库和向量数据本身没有乱码。

## 7. 统一 Markdown 管线复验

2026-07-14 完成重构后，重新验证的当前链路为：

```text
PDF / DOCX / TXT / MD / 图片
→ 初始 Markdown
→ 第一次结构化 draft 切片
→ 仅含图 chunk 调用 qwen3-vl-plus
→ 分类写 metadata、描述/OCR回填 Markdown
→ 文档概述与超长块二次整形
→ BGE-M3 → Milvus Markdown chunk
→ search/chat 读时生成图片预签名 URL
```

2026-07-14 当时的复验结果：

- 当时单元与 API 契约测试 65/65，阶段集成测试 53/53；新增用例覆盖 Docker `/ready` 的成功与失败语义。
- `doc_id=21` 强制重入库后生成 3 个 `21:m:*` chunk，全部为 `content_type=markdown`；含图片 chunk 同时保留附近正文、`#img:8`、图片说明和 OCR。
- `/search.hits[].text` 与 `/chat.refs[].text` 返回 Markdown；API 响应中的图片占位符按请求生成预签名 URL，`body_markdown`、Milvus 和聊天日志仍保存稳定 `#img:{id}`。
- 当时 17 篇成功文档全部有 `body_markdown`；Milvus 共 163 个 Markdown chunk，旧 `:t:`/`:i:` ID 和持久化 URL 均为 0。

因此，第 1–6 节验证的旧独立图片能力已被统一 Markdown 管线覆盖。当前最终验收已经扩展为 80/80 单测、23 个成功文档和 198 个 Markdown chunk，应以 [RAG完整回归测试报告](RAG完整回归测试报告_2026-07-15.md) 为准。
