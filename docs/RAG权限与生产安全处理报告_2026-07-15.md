## 1. 本次完成内容

### 1.1 双层身份信任边界

生产请求必须依次通过两层校验：

1. 上游 Node/API Gateway 使用 `Authorization: Bearer <RAG_SERVICE_TOKEN>` 证明请求来自可信内部服务；
2. 网关在验证终端用户登录态后追加 `X-RAG-User-Id`；RAG 不直接相信该值，而是重新查询 `oa.sys_user`、`oa.sys_employee`、`oa.sys_user_role` 和 `oa.sys_role`，仅接受活动账号、活动员工和当前有效角色。

浏览器和终端用户不得持有 `RAG_SERVICE_TOKEN`，也不得绕过网关直连 RAG。`POST /documents/{id}/ingest` 属于服务操作，只要求服务身份；文档读取、`/search`、`/chat` 还必须有有效用户身份。

### 1.2 文档与案件权限矩阵

| `permission_level` / 数据类型 | 允许访问条件 |
|---|---|
| `public` | 任一已认证活动用户 |
| `internal` | 任一活动员工 |
| `department` | `kb_document.source_department_id` 与用户部门一致 |
| `private` | `author_employee_id` 为本人，或 `created_by` 为本人用户 ID |
| `case` | 用户是案件分配成员、主办律师或案件管理员 |
| 任意绑定 `case_id` 的文档 | 必须同时具备案件成员关系；即使误标 `public` 也不能绕过 |
| 未绑定 `case_id` 的 `case_material` | 按私有文档处理，仅所有者可见，避免脏数据扩大权限 |
| 未知/空权限值 | 默认拒绝 |

管理员仅在以下任一条件成立时获得文档权限绕过：角色编码命中 `AUTH_ADMIN_ROLE_CODES`、角色 `data_scope=all`，或 `permission_json` 显式包含 `rag.admin`。即使是管理员，带 `case_id` 的问答仍不能召回另一案件材料。

### 1.3 检索和问答隔离

- `/search` 和 `/chat` 不再直接使用客户端传入的 `doc_ids`，而是先查询 PostgreSQL 得到服务端授权后的显式文档 ID 列表，再传给 Milvus。
- “授权结果为空”的 `[]` 与“不限制”的 `None` 严格区分；空列表直接返回空检索结果，不创建 collection、不编码 query，也不会退化成全库检索。
- 带 `case_id` 的问答只能使用全局法规和当前案件材料，跨案件文档在送入 Embedding/Reranker/LLM 之前被排除。
- 认证启用时忽略客户端 `user_type`，聊天日志的 `user_id` 强制取数据库校验后的身份；请求体伪造其他 `user_id` 返回 403。
- 无权查看的文档/案件统一返回 404，避免泄露资源是否存在。

### 1.4 生产安全基线

- `APP_ENV=production` 时，认证未启用或 Token 少于 32 字符，应用拒绝启动；`/ready` 同时报告 `authentication=misconfigured` 并返回 503。
- 生产强制关闭 `/docs`、`/redoc` 和 `/openapi.json`。
- 移除通配 CORS；只有显式 `CORS_ALLOWED_ORIGINS` 才启用跨域。
- 增加 Trusted Host 校验、1 MiB 默认请求体上限，并同时限制 `Content-Length` 和分块传输。
- 响应增加 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`；生产增加严格 CSP。
- MinIO 预签名链接默认有效期由 3600 秒缩短为 300 秒，且仍只在授权读取时生成，不写入 PostgreSQL、Milvus 或聊天日志。
- Docker 镜像使用 `rag` 非 root 用户，应用代码由 root 只读持有；Compose 对 RAG 容器启用只读根文件系统（仅 `/tmp` 为临时内存盘）、`cap_drop: ALL` 和 `no-new-privileges:true`，端口继续只绑定 `127.0.0.1`。
- 认证拒绝、文档允许/拒绝、检索授权范围和案件拒绝写入结构化应用日志；问答内容与引用继续写 `ai_chat_log`，日志不记录服务 Token。

## 4. 生产启用步骤

当前根 `.env` 未被自动写入真实密钥，常驻实例的 `/ready` 显示 `authentication=disabled`。这是有意保留：截至后续补录时，平台 RAG 基础代理已经实现，但登录/JWT、可信用户上下文和 `X-RAG-User-Id` 注入尚未实现；直接启用会使现有开发调用全部变成 401，也不能形成完整的终端用户授权链。

正式启用时执行：

1. 在秘密管理系统生成至少 32 字符的随机 `RAG_SERVICE_TOKEN`，分别注入 Node/API Gateway 与 RAG 容器；不要提交到仓库、前端代码、测试报告或日志。
2. 根 `.env` 设置：

   ```dotenv
   APP_ENV=production
   AUTH_ENABLED=true
   RAG_SERVICE_TOKEN=<secret-manager-injected-value>
   EXPOSE_API_DOCS=false
   CORS_ALLOWED_ORIGINS=
   TRUSTED_HOSTS=localhost,127.0.0.1,rag-api,law-rag-kb
   MINIO_PRESIGNED_EXPIRES_SECONDS=300
   ```

3. Node/API Gateway 完成登录态校验后再调用 RAG，并附加：

   ```http
   Authorization: Bearer <internal-service-token>
   X-RAG-User-Id: <authenticated-sys_user-id>
   ```

4. 由反向代理终止 TLS，并配置每用户/每 IP 限流、连接/请求超时、最大请求体和访问日志；RAG 端口不对公网发布。
5. 为 PostgreSQL 和 MinIO 创建独立最小权限服务账号，轮换当前开发凭据；备份、恢复演练和密钥轮换属于部署环境操作，不在本次代码变更中自动执行。
6. 在 `kb_document` 创建/同步流程中强制填写 `permission_level`；部门资料填写 `source_department_id`，个人资料填写 `author_employee_id`，案件材料填写 `case_id`。历史脏数据会被 fail-closed 拒绝，但应完成数据补齐。
7. 启动后确认 `/ready.authentication=ok`，再从网关执行所有者、同部门、跨部门、案件成员和非成员五类验收。

认证模式下运行测试/性能脚本时，通过进程环境设置 `RAG_SERVICE_TOKEN` 和 `RAG_TEST_USER_ID`；脚本不会打印 Token。

## 5. 尚未完成的外部依赖

RAG 自身授权层已完成，但以下工作不属于当前仓库可独立闭环的范围：

- `law-platform-api` 已有 `/api/rag/search`、`/api/rag/chat` 基础代理及服务端 Token/错误脱敏能力，但尚无完整登录、会话/JWT 守卫和已认证用户 ID 注入，因此还不能安全地把当前开发实例切为正式生产入口；
- TLS/WAF/分布式限流、集中日志告警、秘密管理和 Token 自动轮换需要部署平台或 API Gateway；
- 数据库/MinIO 独立最小权限账号需要运维凭据与变更窗口；
- 当前两名活动用户没有可用于“案件成员正向访问”的完整映射样本，本轮真实回归已验证非成员拒绝，正向案件成员场景由自动化策略测试覆盖，平台联调后还需用真实业务账号补验。

因此，本次可判定为：**RAG 权限控制代码、生产 fail-closed 和容器安全基线完成；平台认证代理与正式密钥激活是下一步发布门禁。**
