## 1. 每个问题的根因

### 1.1 chapter 元数据被“节”覆盖

入库代码原先把“编、章、节”共用为 chapter 上下文，正则也把三类标题都识别成 chapter。遇到“第一章 → 第一节 → 第一条”时，`meta.chapter` 最终被“第一节”覆盖，且 Markdown 层级上下文无法独立保留。

### 1.2 不存在文档的入库接口返回 200

`ingest_document()` 把“文档不存在”和普通入库失败折叠为同一种业务失败结果，API 层无法区分资源不存在与可恢复业务失败，因此 `POST /documents/{id}/ingest` 对不存在 ID 返回 HTTP 200。

### 1.3 产品责任法条 Top1 错误

召回阶段其实已把第一千二百零二条排在正确位置，错误发生在交叉编码 Reranker：问题中的“生产厂家要赔吗”与第一千二百零三条的“向生产者请求赔偿”词面更接近，导致 Reranker 将 1203 提升到 1202 之前。

### 1.4 Node lint 与单元测试缺口

主要问题是异常值使用 `any`/不安全断言、流数据块类型未收窄、启动 Promise 未处理，以及 E2E server/response body 类型不明确。项目只有 HTTP E2E，没有隔离的 service 单元测试，MinIO、数据库失败补偿和软删除顺序缺少自动验证。

### 1.5 并发检索慢

阶段计时显示 Milvus 混合检索只占约 5–11 ms；主要瓶颈是 CPU Reranker 的全局模型锁和长短候选同批 padding。5 路时 Reranker 锁等待最高约 18.6 s，单次计算约 2.2–5.8 s。Embedding 计算约 0.2–0.4 s、锁等待最高约 1.2 s，不是首要瓶颈。

直接移除 Reranker 锁的实验反而使 5 路 wall 达约 24.6 s，原因是单模型 CPU 并发导致线程争用；增加 Uvicorn worker 还会重复加载约 1 GiB 模型内存，因此均未采用。

### 1.6 Python 弃用警告与 Node 版本口径不一致

当前 FastAPI 0.139.0 使用 Starlette 1.3.1。Starlette TestClient 优先使用 `httpx2`，依赖缺失时回退到 `httpx` 0.28.1 并发出弃用警告；无需升级 FastAPI、FlagEmbedding 或 transformers。

Node 实际运行环境为 22.22.3 / pnpm 10.32.0，但 README 原写 Node 20，且缺少 `engines`、`.nvmrc` 和 CI 版本约束。

## 3. 关键实现说明

### chapter 与 Markdown 层级

- 独立维护 document section、编、章、节、条五类上下文。
- `meta.chapter` 只接受“第 X 章”，编和节不再覆盖。
- 新编会清理旧章/节，新章会清理旧节；切换节只更新节上下文。
- chunk 文本仍按“编 → 章 → 节 → 条”保留 Markdown 标题，兼顾检索语义和展示。
- TXT 的编/章/节/条也会先提升为 Markdown 标题，再进入统一切分链。

### 404 契约

- 新增 `DocumentNotFoundError`，并在创建/加载 Milvus collection 前完成文档存在性检查。
- API 只把该异常映射为 404；其他入库异常仍保留原 HTTP 200 业务失败结构。
- 对外错误为固定安全文本 `kb_document not found`，不回传内部异常。

### 法律问句归一化

- 召回继续使用用户原始问题，避免扩大召回行为变化。
- 仅对 Reranker 输入做通用法律语言归一化：厂家/厂商/制造商等映射为“生产者”，明确的直接责任意图映射为“承担侵权责任”。
- 没有硬编码文档 ID、chunk ID、法条号或基准答案。
- “撞伤人要赔哪些费用”等赔偿范围问题不会被改写，防止误伤其他法律场景。

### 性能优化

- 增加可关闭的 `SEARCH_TIMING_ENABLED` 埋点：query embedding、Embedding 锁等待/计算、Milvus dense+sparse+RRF 合并阶段、Reranker 锁等待/计算、响应构建/序列化估算和 total。
- pymilvus 的 `hybrid_search` 在客户端接口上是 dense、sparse、RRF 的原子调用，因此生产埋点将其记录为一个准确的合并阶段；诊断时另行执行 dense/sparse 检索用于排名分析。
- Reranker 在不改变模型、候选数、`max_length` 和分数的前提下，按查询加候选长度排序，以 batch size 2 推理，再恢复原候选顺序。该方法减少 padding，保持语义与精度不变。
- 保留单模型锁和 PyTorch 8 线程；没有盲目增加 worker、关闭 Reranker、降低 top_k 或预缓存答案。
