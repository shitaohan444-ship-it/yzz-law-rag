# 数据库设计文档

本文件记录律所 OA 系统在 `law-rag-service` 中的数据库设计来源、schema 结构和当前落地状态。

## 设计来源

- **Excel 设计文件**：`docs/律所综合业务数据库v2.16_最终冻结版.xlsx`
- **Excel 冻结设计**：89 张（源表 80 张 + 统计视图 9 张）、源表字段 1490 个、视图字段 147 个
- **当前数据库（Alembic head `f1a2b3c4d5e6`）**：源表 83 张、统计视图 9 个、外键 207 条、索引 485 个、数据字典类别 145 个、字典项 653 个、总字段 1735 个（源表 1588 + 视图 147）
- 冻结版之后的知识库扩展迁移：`9a7e4c2d6f10`（`kb_document_image` 与 VL 字段）、`d8e9f0a1b2c3`（`kb_document_source`）、`e9f0a1b2c3d4`（`kb_category` 与 `kb_document.category_id`）、`f1a2b3c4d5e6`（知识库软删除与回收站：无新增列，仅回填历史 `deleted`→`purged` 并交换 `file_hash` 唯一索引谓词），上述 83/207/485/1735 已包含

## Schema 位置

所有 OA 业务表均位于现有 PostgreSQL 数据库 `law_rag` 的 **`oa` schema** 下。

应用层连接串示例：

```text
postgresql+psycopg://law_rag_user:law_rag_password@localhost:5432/law_rag?options=-c%20search_path%3Doa%2Cpublic
```

任意层级分类扩展（迁移 `e9f0a1b2c3d4`）：

- 初始化“法律法规”“当事人案件材料”“律所工作资料”“当事人判决案例”及其子分类，并建立系统“待分类”。
- 历史 `法规` 迁入“法律法规 / 法律”，`案例` 迁入“当事人判决案例”，其他旧值、空值和乱码安全迁入“待分类”；迁移后 `kb_document.category_id` 为非空外键。
- 同一活动父节点下分类名称唯一；分类编码创建后不可修改。存在活动子分类或关联文档时不能停用，系统“待分类”受保护。
- “当事人案件材料”子树及“当事人判决案例”具有有效敏感标记；后代通过父链继承敏感性。
- 新 Chunk metadata 保存 `category_id` 和当时的 `category_path` 快照；检索与问答引用会从 PostgreSQL 批量解析最新路径，因此改名或移动分类不需要重建向量。

本次多模态扩展（迁移 `9a7e4c2d6f10`）：

- `kb_document` 新增 `source_type`、`biz_type`、`biz_id`、`case_id`、`dossier_no`、`extra_metadata`。
- 新增 `vl_status`、`image_total`、`image_kept`、`image_filtered`、`vl_processed_at`，用于区分文本入库与图片处理状态。
- `case_id` 可空关联 `case_main.id`，删除案件时置空；已有 `permission_level` 继续作为权限级别字段。
- `kb_document_image` 以 `(document_id, image_sha256)` 唯一，记录出现页码、尺寸、派生对象地址、分类、是否参与 RAG、描述/OCR、模型/提示词版本、token 用量和错误。

统一 Markdown 扩展（迁移链 `f0a1c2d3e4b5` → `a1b2c3d4e5f6`）：

- `kb_document.description_summary` 保存 VL 回填后由文本 LLM 生成的源文件级概述；失败可为空，不阻断正文入库。
- `kb_document.body_markdown` 保存最终 Markdown，图片只使用稳定 `#img:{id}` 占位符，不保存 MinIO 预签名 URL。
- `kb_document_image` 继续作为逐图审计和对象定位来源；VL 分类保存在表字段/向量 metadata，不写入 Markdown 正文。
- Milvus 统一保存 `{doc_id}:m:{idx}`、`content_type=markdown` 的 chunk，不再生成独立图片描述向量。

知识库软删除与回收站扩展（迁移 `f1a2b3c4d5e6`，无新增表与列）：

- 普通删除改为纯软删除：`kb_document` / `kb_document_source` 置 `status='deleted'`、`sys_attachment` 置 `status='soft_deleted'`（均写 `deleted_at`），保留 MinIO 原件、派生图片与 Milvus 向量，可经回收站恢复；永久删除才置 `status='purged'` 并清理原件/图片/向量。
- `status` 取值约定：`active`（在用）/ `deleted`、`soft_deleted`（回收站可恢复）/ `purged`（已永久清理，不可恢复）。检索授权门强制 `status='active' AND deleted_at IS NULL`，软删文档对 `/search`、`/chat` 天然不可见。
- 历史 3.中已硬删（无原件/向量）的 `kb_document`、`kb_document_source`、`sys_attachment(knowledge_base)` 在升级时统一回填为 `purged`，不进入新回收站；该数据回填不可逆。
- `file_hash` 唯一索引 `uk_sys_attachment_public_kb_file_hash` 谓词由 `deleted_at IS NULL` 改为 `status IN ('active','soft_deleted')`：回收站存在相同文件时阻止重复上传（`409`），`purged` 后释放哈希位允许重新上传。

## 关键注意事项

1. **循环依赖**：`sys_department.manager_employee_id` 与 `sys_employee.department_id` 互相引用。外键迁移中先加 `employee.department_id`，最后再加 `department.manager_employee_id`。
2. **软删除**：所有含 `deleted_at` 字段的表统一使用软删除，查询时加 `deleted_at IS NULL`。
3. **自增主键**：使用 PostgreSQL `GENERATED BY DEFAULT AS IDENTITY`。
4. **无效外键（数据库层未加）**：
   - `sys_dict_field_binding.code_category/region_code` 因目标列不唯一。
   - `ops_live_session.host_employee_id`、`operator_employee_id` 字段不存在。
